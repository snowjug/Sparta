# Evaluation

What is measured, how, how far the numbers can be trusted, and how to reproduce them.

**Read this first.** The dataset is synthetic, written by AI assistants for this project, and not reviewed by native
speakers. The numbers below say how the rule engine behaves on that data. They are a regression signal. They are not a
claim about accuracy on real phone calls, real speech recognition, or adversaries who have read the rules.

Published reports (generated by the tool, never edited by hand):

| Split | Purpose | JSON | Markdown |
| --- | --- | --- | --- |
| `dev` | rules and lexicons were tuned on it (many iterations) | [`latest-dev.json`](eval/latest-dev.json) | [`latest-dev.md`](eval/latest-dev.md) |
| `test` | held out; run once for the published numbers | [`latest-test.json`](eval/latest-test.json) | [`latest-test.md`](eval/latest-test.md) |

## 1. What is evaluated

The harness runs each scripted conversation through the real `ConversationEngine`
(`services/api/src/sparta/orchestrator/engine.py`) the way `CallService` drives it: caller turns (with the previous turn
for split-phrase detection) and silence steps. It uses no providers, no database and no clock, so it measures the
**decision logic**: language detection, signal detection, risk scoring, planner templates, output validator and summary.

Not measured: speech recognition, speech synthesis, telephony, network latency, the Azure OpenAI adapter, the Android
app, the web app. The ground-truth language is **not** passed to the engine as a hint, so language detection is
measured from the text alone.

## 2. Dataset (`packages/evaluation/dataset/v1`)

One JSON object per line, validated by `packages/evaluation/scenario.schema.json`:

| Field | Meaning |
| --- | --- |
| `language_profile` | `english`, `hindi`, `hinglish`, `kannada`, `kanglish`, `mixed`, `unsupported` |
| `turns` | up to 14 caller turns: `speech` (text, ground-truth language, `stt_confidence`, `gap_ms`) or `silence` |
| `expected` | `is_scam`, `is_legitimate`, `is_spam_unwanted`, acceptable categories, risk levels and final actions, `required_signals`, `forbidden_signals`, `should_escalate`, `must_end_call`, `must_not_end_call` |
| `prohibited_assistant_behavior`, `leak_markers` | behaviours and strings the assistant must never produce |
| `summary_expectations` | groups of alternative English terms the summary must contain, and terms it must not |
| `tags` | for example `noisy_transcript`, `prompt_injection`, `hard_negative`, `owner_probe`, `bank_otp`, `upi_payment` |

Size and composition (details, per-category counts and SHA-256 checksums are in
[`MANIFEST.md`](../packages/evaluation/dataset/v1/MANIFEST.md)):

- 70 `dev` and 70 `test` scenarios. Per profile and split: english 15, hindi 9, hinglish 15, kannada 9, kanglish 15,
  mixed 4, unsupported 3 (for example Tamil and Telugu callers).
- Scam families: bank/KYC/OTP, government and police threats, courier, tech support and remote access, prizes, UPI and
  payment, gift cards and crypto, jobs, prompt injection, owner probing.
- Benign families: deliveries, appointments, recruiters, support call-backs, family, school or hospital, emergencies,
  plus hard negatives such as a genuine bank alert.

Provenance, stated plainly:

- Every scenario is invented and LLM-authored. No human wrote or labelled them and no native speaker reviewed the Hindi,
  Kannada, Tamil or Telugu text or the romanised spellings.
- Labels are one author's judgement; inter-annotator agreement was not measured.
- 26% of the scenarios in each split are written as noisy, unpunctuated transcripts with author-assigned
  `stt_confidence`. That is not recogniser output.
- The `test` scenarios were written after reading `dev`, with the same taxonomy and label conventions and different
  names, situations and phrasing. They are held out but **not independent**; expect them to be optimistic for unseen
  real traffic.
- Each split has 70 scenarios and individual profiles have 3 to 15. Differences of a few scenarios are noise.

## 3. How scoring works

**Safety measures** (`services/api/src/sparta/evaluation/metrics.py`)

- *Scam flagged*: final risk is `high`, or the final recommended action is `refuse_and_end`, `block_recommended` or
  `report_recommended`. Precision, recall and F1 are over `is_scam` against that flag.
- *Scam calls ended by the assistant*: among scams with `must_end_call`, the share the assistant ended itself.
- *Legitimate calls wrongly ended / rated high*: among `is_legitimate` scenarios (lower is better).
- *Protected-information requests refused*: at the first turn where a protected-class or injection signal first
  appears, did the assistant's reply use a refusal template. Scenarios without such a turn are not counted.
- *Prompt-injection attempts resisted*: refused and the call ended.
- *Prohibited assistant behaviours*: lexical proxies over the English rendering of every assistant utterance
  (`checks.py`): asks for protected data, reveals the owner's planted private facts or availability, claims to be the
  owner, agrees to pay, confirms an unverified identity, follows an injected instruction. A hit means a template or the
  validator regressed.
- *Validator fallbacks* and *non-determinism* (two runs of every scenario must be identical, timings excluded).

The last two and prohibited behaviours must be zero. `sparta evaluate` exits with status 1 if any is not.

**Expectation checks** per scenario: risk level, category, final action, required signals, forbidden signals, ended or
not ended, escalation, behaviours, summary. "All checks pass" needs every one, so it is a deliberately harsh figure.

**Live versus coverage.** When the assistant refuses and hangs up, the rest of the scripted caller turns are never
heard. A scam that is ended early cannot say the rest. So *required signals recognised* is computed over **every
scripted turn** (a shadow pass, `ConversationEngine.detect_signals`), while *required signals raised before the
assistant hung up* counts only what it actually heard. Both are reported; the live figure is the lower one.

**Uncertainty.** Every rate carries a Wilson 95% interval. With these sample sizes the intervals are wide.

**Noise sweep** (`--stt-noise`): words are dropped or have two letters swapped at 10%, 20% and 30%, deterministic and
seeded. This is a stand-in for recognition errors; real recognisers fail differently (homophones, code-switching,
truncated words).

**Latency** is the decision logic only, over engine steps.

## 4. Discipline

1. Rules, lexicons and thresholds were tuned on `dev` only, over many iterations. The `dev` numbers are therefore
   **training-set numbers**, published for transparency and not as a result.
2. The `test` split was run **once**, in a single invocation that also ran the noise sweep, with the engine as of commit
   `b09c936`. Rules, lexicons, thresholds and policy have not changed since (policy 2026.11.2). Later commits did change
   code the run exercises: `ef1e21f` (the Markdown renderer only, `MIN_TAG_SLICE`), `f263382` (the summary no longer
   repeats a generic organisation word, "a bank (Bank)"), `ac59c3e` (no behaviour change: a hashing flag and comments)
   and `117752e` (security review: bounded input work, deletion of invisible characters and folding of look-alike
   letters in `language/text.py`, `risk/matchers.py` and `orchestrator/engine.py`; see
   [`SECURITY_REVIEW.md`](SECURITY_REVIEW.md)).
   The `test` split was **not re-run** after them. Two checks stand in for a re-run, and neither is one: the `dev`
   report regenerated with the final code is identical to the committed one apart from timestamps and timings, and a
   character scan of both splits (counts only, no reading of scenarios) found no compatibility forms, no Cyrillic or
   Greek letters, no turn longer than 223 characters, and only U+200C, always next to Indic letters, where the handling
   is unchanged by design. If a re-run is ever published it must be labelled as a second run.
3. Failing `test` scenarios are withheld from the report (`--details` exists and must not be used for tuning). If the
   split is ever used for tuning, it is burned and a new held-out split has to be written.
4. The gap between the two splits is reported as it came out.

### How to read them

- **What held up:** refusing protected requests (35 of 35 held out, 0.0% to 9.9% miss at the 95% level), zero
  prohibited behaviours, zero validator fallbacks, deterministic output, and language detection per turn and per call.
  These are the properties that come from the design (vetted templates, validator, deterministic rules), not from
  tuning.
- **What did not:** recall and signal coverage fell sharply from `dev` to `test` (scam recall 87.8% to 75.6%, required
  signals recognised 95.9% to 67.9%). The most likely reading is that the lexicons are fitted to `dev` phrasing. That
  is an interpretation; the data does not prove the cause.
- **False alarms on legitimate calls are not rare enough:** 3 of 21 legitimate `test` calls were rated high risk and 1
  was ended. The interval on that is 0.9% to 22.7%.
- **Owner-probing, mixed-language and unsupported-language scenarios are weak** on `test` (scam flagged 3 of 8, 1 of 3
  and 0 of 1 in the respective slices). The last two slices are tiny.
- **Summary check:** 40.0% on `test`. The check looks for topical words; the template summary does not aim for them.
  Treat it as a weak proxy, not as a verdict on summary usefulness.
- **Noise:** recall degrades steadily with synthetic noise (58.5% at 30%), and legitimate calls get ended more often.
- **Forbidden-signal failures** on `dev` are legitimate callers (delivery agents, recruiters) that raise
  `IMPERSONATION_COURIER` or `IMPERSONATION_EMPLOYER`. That is partly a labelling mismatch: the signal means an
  unverified identity claim, which a genuine caller also makes. The `test` failures are withheld.

## 6. Known gaps that the dataset does not cover

- **Denials versus requests.** "No OTP is needed", "never share your PIN" and their Hindi and Kannada forms are
  recognised as denials per mention (`risk/matchers.py`, `[negation]` in `risk/policies/default-v1.toml`). Residual
  risks, each of which can cause a miss: conditional demands such as "no OTP, no refund", pronoun follow-ups after a
  denial ("do not share your OTP with anyone. Just read it to me"), transcripts without punctuation, and unsupported
  languages: on `dev`, the Tamil bank scenario `un-tamil-bank-01` is rated low risk and its OTP request is missed.
- **Real audio.** Recognition errors, accents, crosstalk and silence handling were never measured on audio.
- **Adversaries.** Someone who reads the rules can phrase around them. Only a few injection scenarios are included.
- **Other languages.** Marathi, Tamil, Telugu, Malayalam and Bengali packs exist as `planned`; callers in those
  languages are asked to switch to a supported language and risk rules still run on the text.
- **LLM assistance.** The evaluation calls no language model. The optional Azure OpenAI adapter (off by default) was
  never run against a live service and is not part of these numbers.

## 7. Reproduce

From `services/api` (Python 3.12+, dependencies installed; the dataset path defaults to
`../../packages/evaluation/dataset/v1`).

Windows PowerShell:

```powershell
cd services\api
.\.venv\Scripts\python.exe -m sparta evaluate --split dev --stt-noise `
  --out '..\..\docs\eval\latest-{split}.json' --markdown '..\..\docs\eval\latest-{split}.md'
```

Linux or macOS:

```bash
cd services/api
python -m sparta evaluate --split dev --stt-noise \
  --out '../../docs/eval/latest-{split}.json' --markdown '../../docs/eval/latest-{split}.md'
```

Use `uv run sparta evaluate ...` if you manage the environment with `uv`. Without `--out` and `--markdown` the command
prints a one-line summary and exits with status 0, or 1 if a safety invariant was violated. The `dev` split with the
noise sweep took about 90 seconds on the development machine. Re-running it reproduced the committed report exactly
apart from the timestamp and latency timings. Do not run `--split test` or `--split all` while tuning rules, and do not
overwrite `docs/eval/latest-test.*` unless you are publishing a new held-out run.

Related tests: `services/api/tests/unit/test_signals.py` (risk signals and denial handling),
`tests/unit/test_extraction.py` (claim extraction), `tests/unit/test_language.py` (detection),
`tests/unit/test_planner_validator.py` (templates and validator), `tests/integration/test_call_service.py` (call
flow).

## 8. Before relying on any number

A real evaluation needs native-speaker review of the Hindi, Kannada and romanised text, human labels from more than one
annotator, recorded calls with consent and real recogniser output, a fresh held-out split written by someone who has not
seen the rules, and a larger sample. None of that exists yet.
